# CONTEXTO MESTRE — TECH CHALLENGE FASE 3

Você atuará como engenheiro de software / machine learning responsável pela implementação de um Tech Challenge acadêmico de Inteligência Artificial.

IMPORTANTE:
Não implemente tudo de uma vez.

O projeto será desenvolvido em etapas.
Antes de iniciar cada etapa:
1. revise a arquitetura;
2. informe resumidamente o que será criado;
3. implemente somente a etapa solicitada;
4. execute testes;
5. apresente os resultados;
6. não avance para a etapa seguinte sem solicitação.

O projeto deve ser funcional, reproduzível, modularizado, documentado e adequado para demonstração acadêmica.

==================================================
1. OBJETIVO DO PROJETO
==================================================

Construir um Assistente Clínico Inteligente capaz de apoiar médicos no acompanhamento de pacientes.

O assistente deve:

- responder perguntas clínicas;
- consultar informações estruturadas de pacientes;
- identificar exames ou informações pendentes;
- consultar protocolos clínicos;
- contextualizar respostas com informações atualizadas do paciente;
- apresentar fontes utilizadas;
- sugerir possíveis próximos passos previstos em protocolos;
- gerar alertas;
- aplicar regras de segurança;
- exigir validação humana quando houver decisão clínica;
- registrar logs para auditoria.

O assistente NÃO substitui profissionais médicos.

O projeto é acadêmico e utilizará dados públicos e/ou sintéticos.

==================================================
2. CASO DE USO DO MVP
==================================================

O MVP será inicialmente focado em:

"Assistente Clínico para Apoio ao Acompanhamento de Pacientes com Asma"

O escopo pode ser ampliado posteriormente, mas a primeira versão deve permanecer focada para garantir qualidade e conclusão do projeto.

Exemplo de cenário:

Paciente PAC001
- diagnóstico: asma;
- consultas anteriores;
- medicamentos;
- observações clínicas;
- exames realizados;
- exames pendentes.

Pergunta do médico:

"Este paciente possui exames pendentes e qual deve ser a próxima ação de acordo com os protocolos?"

O sistema deverá:

1. identificar o paciente;
2. consultar o banco estruturado;
3. identificar exames pendentes;
4. buscar protocolos relevantes;
5. construir contexto;
6. consultar a LLM customizada;
7. avaliar a segurança da resposta;
8. indicar fontes;
9. indicar se validação humana é necessária;
10. registrar toda a execução em log.

==================================================
3. REQUISITOS OBRIGATÓRIOS DO TECH CHALLENGE
==================================================

A implementação precisa obrigatoriamente cobrir:

### Fine-tuning

Realizar fine-tuning de uma LLM usando exemplos relacionados a:

- protocolos médicos;
- perguntas frequentes feitas por médicos;
- modelos de laudos;
- modelos de receitas;
- procedimentos internos.

Os dados deverão passar por:

- preprocessing;
- limpeza;
- anonimização;
- normalização;
- curadoria;
- preparação para treinamento.

O fine-tuning deve ser REALMENTE executado.

Não é suficiente apresentar apenas código de treinamento.

Precisamos armazenar evidências como:

- training loss;
- validation loss, quando aplicável;
- parâmetros de treinamento;
- checkpoints/adapters;
- métricas;
- logs.

### LangChain

Utilizar LangChain para:

- integrar a LLM customizada;
- executar ferramentas;
- consultar dados estruturados;
- consultar protocolos;
- construir contexto;
- gerar respostas contextualizadas.

### LangGraph

Utilizar LangGraph para controlar o fluxo de decisão.

Deverá existir pelo menos um fluxo real envolvendo:

receber pergunta
→ localizar paciente
→ consultar prontuário
→ verificar pendências
→ buscar protocolo
→ gerar resposta
→ safety check
→ human-in-the-loop quando necessário
→ logging
→ resposta final.

### Segurança

O assistente não pode:

- realizar prescrição autônoma;
- modificar medicamentos;
- afirmar diagnóstico definitivo sem validação;
- inventar informação ausente;
- esconder a origem da informação utilizada.

Ações clínicas devem poder exigir validação humana.

### Logging

Registrar informações suficientes para auditoria:

- execution_id;
- timestamp;
- patient_id;
- pergunta;
- ferramentas utilizadas;
- documentos recuperados;
- fontes;
- modelo utilizado;
- resposta;
- resultado da validação de segurança;
- necessidade de validação humana;
- decisão humana, quando houver.

### Explainability

A resposta deve apresentar a origem das informações utilizadas.

Exemplo:

Fonte:
- Protocolo Interno ASM-002 — seção 3.1
- Diretriz clínica X — seção Y
- prontuário do paciente PAC001

==================================================

Modelo principal proposto:

Qwen3-8B

Objetivo:

realizar fine-tuning eficiente usando QLoRA / LoRA.

Tecnologias previstas:

- Python;
- Hugging Face Transformers;
- PEFT;
- TRL;
- bitsandbytes;
- PyTorch.

O modelo base deverá permanecer separado do adapter LoRA sempre que for tecnicamente conveniente.

Estrutura conceitual:

Qwen3-8B
      ↓
Baseline
      ↓
QLoRA
      ↓
Adapter treinado
      ↓
Qwen3-8B + Adapter
      ↓
Modelo customizado

IMPORTANTE:

A escolha Qwen3-8B é uma decisão de arquitetura do projeto e não uma exigência acadêmica.

Caso o ambiente disponível não suporte o modelo de 8 bilhões de parâmetros:

NÃO trocar silenciosamente o modelo.

Primeiro:
1. diagnostique a limitação;
2. informe memória/GPU necessária;
3. proponha uma variante menor compatível;
4. aguarde aprovação.

==================================================
5. FINE-TUNING E RAG POSSUEM FUNÇÕES DIFERENTES
==================================================

Não transformar o RAG em substituto do fine-tuning.

O trabalho exige fine-tuning.

Arquitetura:

FINE-TUNING
→ ensina comportamento;
→ estilo institucional;
→ estrutura de respostas;
→ regras;
→ padrões de laudos;
→ FAQs;
→ procedimentos.

RAG
→ fornece conhecimento atual;
→ protocolos;
→ documentos;
→ diretrizes;
→ versões atualizadas das fontes.

Portanto:

Fine-tuning + RAG devem coexistir.
